# Docker 项目与服务操作设计

设计日期：2026-11-04。发布状态更新：2026-11-17。

1.5.0 已包含容器/项目只读导航、单容器操作与临时日志/inspect。本文的项目/服务组生命周期操作（`GroupActionPlan` 等）仍为后续设计，不属于本次发行功能。下文保留原型设计与当时的验收计划，当前使用方法以 README 为准。

## 产品边界

在第七页 Docker 中提供「容器 / 项目」两个视图，沿用彩色分块、中文状态、滚动和 SSH 小终端保护。默认仍显示容器。项目视图识别已有容器的 Compose 标签，不扫描磁盘、不执行 Compose 文件、不新增守护进程，不保存历史、日志或操作记录。

首期项目操作明确命名为「启动已有容器 / 停止运行容器 / 重启运行容器」。它是已确认容器集合上的生命周期操作，不等价于 Docker Compose 编排，不自动创建缺失服务、读取依赖、按健康检查排序、拉取镜像或应用新配置。没有容器的项目或服务无法仅靠标签发现；页面必须说明这一点。

## 页面与交互

| 层级 | 显示内容 | 操作范围 |
|---|---|---|
| 项目列表 | 项目名、已发现服务数、容器数、运行/停止/异常数 | 进入项目详情 |
| 项目详情 | 按服务分块、各副本状态、已有容器数 | 显式选择整个项目或某个服务 |
| 服务详情 | 所有已有副本、健康检查、CPU/内存 | 当前服务的已有容器 |
| 容器详情 | 现有容器详情与只读入口 | 单个完整容器 ID |

建议 `v` 切换容器/项目视图；项目视图 `n/b` 选择、Enter 进入、Esc 返回，`o` 打开当前层级操作面板。页面上持续显示当前层级和范围，不能从容器详情隐式扩大成整个项目。原有 `g/c/m`、滚动和全局暂停保留。尚未最终分配的按键必须经终端回归确认。

资源汇总只加总同一有效快照中的已知指标；存在缺失时标注「部分容器有读数」，不把缺失当零。CPU 仍按一个虚拟 CPU 为 100%，内存限制不相加成所谓项目总容量。健康只统计运行且配置了检查的容器。

## 动作计划与确认

独立的不可变 `GroupActionPlan` 保存范围、动作、连接身份、项目/服务、全部成员完整 ID 和状态指纹、实际执行子集、排除原因及采样时刻。复用单容器目标字段；新增服务身份和一次性容器标记。`com.docker.compose.oneoff=True` 的运行任务默认排除，缺失或不明确的归属不得猜测。

| 动作 | 候选目标 | 不执行的成员 |
|---|---|---|
| 启动已有容器 | created / exited | 已运行、暂停、异常生命周期 |
| 停止运行容器 | running 且非 AutoRemove | 已停止、暂停、自动删除、异常状态 |
| 重启运行容器 | running 且非 AutoRemove | 已停止、暂停、自动删除、异常状态 |

用户明确看到已排除成员及原因后才能确认；候选为空则禁用。缺失必要安全字段的候选不生成计划。项目级暂停/恢复暂不提供，单容器已有入口保留。

确认页显示：引擎/context、项目、服务或整个项目、动作、将影响的全部容器、排除项、可能中断服务及无依赖顺序保证。默认取消，选择确认后 Enter 提交。长列表可滚动，但必须完整查看目标与警告后才启用确认；窗口缩小或计划变化使确认失效。所有规则在键盘处理层检查，不依赖画面文字。

## 后台执行与部分结果

1. 全局只允许一个有副作用的任务，单容器和组操作共享互斥门；只读查看独立。
2. 绑定原用户身份、context、本地 Unix endpoint、engine ID。计划超过 30 秒必须重新生成。
3. 提交前重新获取全部项目/服务成员和状态指纹。新增、删除、同名替换、服务变化或状态改变均拒绝旧计划，回到预览；不能悄悄扩大或缩小范围。
4. 完成整组预检后，按固定 ID 顺序串行操作；每个目标前再检查身份和状态。该顺序只为可预测，不宣称依赖顺序或 Compose 语义。需要依赖编排的用户使用 Compose 原命令。
5. 每个命令最多等待 60 秒，整组总预算 120 秒；预算耗尽不发出下一条命令。超时或某个目标异常即停止后续操作，不自动重试、不反向回滚。退出阻止尚未提交的下一项，但已交给引擎的请求可能继续。
6. 逐项查询最终状态，在同一会话显示「已核实 / 未执行 / 结果未确认」。组内部分完成必须显式标为部分完成；CLI 成功不等于应用就绪。

Docker 没有原子 compare-and-act 或多容器事务。即使整组预检通过，其他客户端仍可能在最后检查后修改同一对象；不能承诺原子性、完全消除竞态或自动恢复服务。

## 真正的 Compose 工作流

`up`、`pull`、`down`、`build`、重建和配置应用留到独立后续阶段。需要用户显式指定项目目录与配置文件，并处理多文件、profiles、环境变量、插件缺失及依赖关系；容器标签中的路径不能视为可信执行授权。不能通过扫描用户目录或对未知配置运行命令自动解决。

当前命令参考只显示静态示例，不承诺剪贴板复制。SSH 本机剪贴板与远端剪贴板不同，未来若增加复制，必须明确具体机制且由用户主动触发。

## 已完成：只读入口与项目/服务导航原型（2026-11-04）

- 日志命令并行排空 stdout/stderr，分别最多缓冲 64 KiB；设 5 秒期限，失败只显示脱敏错误，成功时保留两个流并标注截断。
- 只读请求固定容器 ID、context、endpoint、引擎 ID；拒绝过期快照、连接或引擎变化；结果带目标名称/context。
- `x` 清除当前临时结果并终止在途 Docker 子进程；程序退出时也清理。终端控制序列移除，保留日志换行。
- `v` 切换项目视图；`n/b` 选项目，Enter 展开服务及现有容器，Esc 收起。项目视图只读；`o` 会被拒绝并提示，不存在组操作。
- 项目服务资源汇总只加总已知值，样本缺失明确标注，不补零。
- 当前测试覆盖输出硬上限、stdout/stderr、CLI 错误脱敏、项目层只读和部分指标缺失；尚未覆盖真实 Docker 日志管道的压力/超时/取消全部边缘场景，亦未部署现场验证。

该原型不实现 Compose 组控制。实现前仍需补齐的事项：

当前源码复查发现上一轮只读入口还需补齐，先前「完成」仅代表原型及已有测试通过：

- `docker logs` 的应用 stderr 不能丢失，也不能与 CLI 错误混淆；同时保留 stdout/stderr，非零退出返回脱敏错误。
- 目前先完整 `communicate()` 再截断，不能保证子进程输出内存有界。改为读取期间限制字节数和运行时间，到限截断并标明，不能只依赖 `--tail` 限制单行大小。
- 将 context、endpoint、engine ID、完整容器 ID 固定到请求；传递用户指定 context，拒绝失效/暂停的旧选择。结果标注原目标，不能随着选择变化而被误认为另一容器的数据。
- 请求可取消、线程启动失败能恢复、退出时清理子进程和线程；关闭查看立即清空会话缓冲。保留真实换行，过滤 ANSI/终端控制字符，显示截断提示。
- 日志本身可能含令牌或业务信息；inspect 白名单不等于日志自动脱敏。README 必须分别表述，不能承诺日志没有 Secrets。安全摘要使用中文字段，不直接倾倒原始 JSON。

## 验收与实施顺序

先修只读入口，再加入只读项目/服务导航，最后加入已有容器组生命周期操作。每一步单独验证并更新预览部署记录。

自动回归覆盖：多副本、独立容器、one-off、空项目、部分缺失读数、成员变化/同名替换、引擎变化、过期确认、重复提交、串行部分失败、预算耗尽、退出取消、小终端与缩放、超长名称、日志双流/超长单行/敏感原文边界、只读线程清理。

现场验证只使用独立临时测试项目，验证两个服务与多副本、成员增减、部分失败及默认取消；不控制已有业务容器。Mac mini/OrbStack、真实 sudo、其他运行时的结果分别记录，不把模拟测试等同于现场验证。不在本轮设计任务中创建容器、部署或发布。
